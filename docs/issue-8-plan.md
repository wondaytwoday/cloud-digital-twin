## 검토 결론

서버 캐시를 다시 만드는 것보다 **브라우저가 받아서 처리하는 데이터 축소**, **대표 자원과 네트워크 구조가 보이는 지도**, **미선택 데이터를 보존하는 선택 수집**이 효과가 크다. 작은 오류와 측정 기반을 먼저 정리하고 이 세 가지를 단계적으로 구현한다.

이슈 작성자는 VM 크기, AWS 계정 순환, 조직 비용, 구형 캐시, GCP 빈 비용 처리의 개선을 실환경에서 확인했다고 기록했다. gzip·ETag·304도 효과가 확인됐으며 남은 병목은 클라이언트 처리다. 이는 작성자의 검증 기록이며 이번 세션의 독립적인 실환경 재검증 결과는 아니다. 프록시 안정성은 여러 회차 관찰이 더 필요하다.

### 제안을 그대로 적용하면 안 되는 부분

1. **화면 캐시는 이미 있다.** `src/App.tsx`의 시나리오·화면별 캐시와 일부 축약 응답을 유지한다. 처음 방문하는 서로 다른 화면에서 공통 자원 데이터가 반복 전송·검증되는 문제를 줄인다. 모든 화면이 항상 전체 스냅샷을 받는다고 전제하지 않는다.
2. **정책 숨김과 공간 배치도 일부 구현돼 있다.** 기본 정책 표시가 꺼져 있고 정책 배지와 VM→서브넷→VPC 부모 관계가 있다. 실제 기본 화면에 남는 노드 수와 배치를 측정한 뒤 집계·범위 분리를 고친다. 원본 링크에서 정책 비중이 높다는 사실을 기본 화면의 표시 비중과 혼동하지 않는다.
3. **선택 수집은 병합 모델이 먼저다.** 지금의 제공자·계정 단위 성공 판정으로 자원 종류만 걸러 수집하면 미선택 자원을 삭제할 위험이 있다. 항목별 소유 범위와 완료 상태를 모델에 추가한 뒤 API와 버튼을 만든다.
4. **동시성 증가 전에 제한 누락을 보완한다.** `server/collectors.ts`의 AWS `resources` 콜백은 SDK에 직접 요청한다. IAM 등에서 사용하는 `single()`의 공통 요청 제한을 거치지 않는다. 계정·리전 전체의 요청 상한을 보장한 뒤 IAM을 병렬화한다.
5. **`COLLECT_MINUTES=0`의 비활성화 의미를 보존한다.** 무조건 양수만 허용하는 수정은 문서의 사용법을 깨뜨린다. 현재 `needsCollection`은 0에서도 시작 수집을 유도하므로 자동 시작·주기 수집 비활성화와 수동 실행 허용을 명시적으로 구분한다.
6. **체크포인트 복사 제거만으로 최적화하지 않는다.** 변경 가능한 객체를 공유하면 타임아웃 이후 저장 내용까지 바뀔 수 있다. 완료된 조각을 불변으로 확정하고 저장 시점에만 합치는 구조로 바꾼다.

### 선택 수집의 데이터 보존 계약

`provider → scope → collection item → region(필요 시)` 단위로 소유 영역과 결과를 기록한다. 비용은 실제 조회 단위가 계정과 다를 수 있으므로 별도 단위를 유지한다.

- 상태는 미선택, 미지원, 성공한 빈 결과, 성공, 부분 실패, 실패, 대기를 구분한다. 완료 시각은 실제 완료한 항목에만 갱신한다.
- 완전히 성공한 영역만 새 결과로 교체한다. 미선택 영역은 기존 값·시각을 유지하고 실패 영역은 마지막 정상 데이터를 보존한다. 동일 kind라는 이유로 다른 항목의 자원을 지우지 않는다.
- 자원뿐 아니라 링크·계층·IAM·비용·활동·요약의 소유 범위도 정의한다. 미해결 참조는 미해결로 남기며 부모 자원을 지어내지 않는다.
- 요청은 전체/선택 모드를 명시한다. 기존 body 없는 전체 요청은 호환한다. 선택 모드의 빈 배열·알 수 없는 항목·제공자 불일치는 400으로 거부한다. JSON 크기 제한과 기존 권한·범위 검사·감사 기록을 유지한다.
- 같은 요청의 중복 실행은 기존 실행으로 안내할 수 있다. 다른 선택으로 실행 중인 작업에는 409와 실행 ID를 반환해 새 작업이 시작됐다고 오해하지 않게 한다.
- VM 조회에 필요한 NIC·서브넷 등 의존 항목은 서버에서 계산하고 UI에 표시한다. 비용·활동 같은 무관한 항목을 암묵적으로 실행하지 않는다.
- AWS는 선택하지 않은 서비스 API가 호출되지 않는지 확인한다. Azure는 ARG 필터와 관계 정보의 충분성을, GCP는 assetTypes 필터와 계층 수집을 검증한다. 전체 inventory 조회를 뒤에서 무조건 실행하면 선택 수집의 목적을 달성하지 못한다.
- UI에는 제공자·항목 체크박스, 의존 항목, 마지막 성공 시각, 미수집/실패 상태를 제공한다. 선택 완료 결과도 유효한 세대로 확정한 뒤 공개한다.

### 응답·캐시·저장 계약

- `ResourceSummary`, 지도 표시 모델, 화면 메타데이터 등에 각각 런타임 검증을 정의한다. 범위 제한은 서버에서 페이지 분할보다 먼저 적용한다.
- 공통 `dataRevision`을 진행 상태 변경과 분리한다. HTTP ETag는 화면·압축 등 표현별 값이므로 화면 공통 데이터 버전으로 재사용하지 않는다. 수집 시각 하나만으로 데이터 변경을 판정하지 않는다.
- 페이지 커서는 데이터 세대와 필터에 연결한다. 조회 도중 세대가 바뀌면 명시적으로 재시작시키며 행이 조용히 누락·중복되지 않게 한다. 캐시는 사용자·권한·범위를 격리하고 크기를 제한한다.
- 응답을 먼저 줄인 뒤 파싱·검증이 여전히 주 스레드 병목일 때 Worker를 검토한다. 큰 객체를 Worker와 복제하는 비용도 측정한다.
- 활동 저장 분리는 포털 자체 감사 기록과 구별한다. 활동 조각을 먼저 확정하고 스냅샷과 같은 세대를 가리키는 manifest를 원자적으로 공개한다. 보존 기간·잘린 결과 여부·실패 범위를 표시한다.
- 기존 version 1은 계속 읽고 전체 JSON 내보내기는 필요한 데이터를 합쳐 기존 계약을 유지한다. 내부 저장 형식의 버전·이행·복구 절차는 별도로 문서화한다. 새 세대 검증 전에 원본 파일을 삭제하지 않는다.
- 파일 수정 시각을 수집 성공 시각으로 대체하거나 저장 시 live 검증을 건너뛰지 않는다.

### 지도 범위와 정확성

- 기본 화면의 목표 노드 예산은 컨테이너를 포함해 약 60개로 잡고 측정 후 조정한다. 초과 시 상위 집계와 상세 진입을 제공하며 자원을 설명 없이 잘라내지 않는다.
- 지역 묶음 키에 계정/구독/프로젝트 범위를 포함한다. 같은 리전의 다른 계정을 하나의 네트워크 공간처럼 합치지 않는다.
- 일반 service·설정·보안 항목은 기본 노드보다 수량·목록·정책 배지로 표시한다. 실제 appliance·gateway·endpoint는 필요한 경로에 남긴다.
- 네트워크 위치가 없는 관리형 서비스나 저장소를 임의의 VPC 안에 넣지 않는다. 다중 NIC·서브넷은 첫 번째 값으로 단일 위치를 단정하지 않는다. 논리적 `contains`와 공간적 `parent`를 유지한다.
- 참조 관계, IAM 할당, 정책 설정, 관측 통신은 서로 다른 의미다. 구조상 경로가 있다는 이유만으로 통신 허용을 표시하지 않는다. 정책 평가가 충분하지 않으면 판단 불가로 표시한다. firewall 정책은 경유 장비로 넣지 않는다.
- 기존 SVG/draw.io 내보내기를 확장해 현재 범위·집계·배지와 일치시키고 XML escape를 검증한다. UI에 없는 별도 전체 지도를 내보내지 않는다.

## 측정과 검증 계획

다음 수치는 **제안 목표이며 현재 측정값이 아니다.** 작은 fixture와 다계정·다리전 합성 데이터(핵심 10,000 + 부속 40,000 + 활동 100,000)를 사용한다. 반복 문자열만으로 압축 효과를 과대평가하지 않도록 이름·속성·관계의 분포를 다양하게 만든다.

| 영역 | 비교할 지표와 제안 목표 |
|---|---|
| 브라우저 | 같은 기기·빌드에서 최초 진입과 재방문을 구분해 20회 측정. 전송·파싱·Zod·렌더·레이아웃 시간을 분리 |
| 검색 | 입력 처리 p95 50ms 이내를 우선 목표로 설정. debounce를 포함한 결과 반영은 약 300ms를 목표로 조정 |
| 목록 | 첫 100행 조회에 전체 자원 배열을 보내지 않음. 요약 응답 비압축 300KB 이하를 초기 예산으로 검토 |
| 화면 전환 | 캐시가 있는 화면에서 입력 후 반응 p95 150ms 이내를 초기 목표로 설정 |
| 지도 | 기본 노드 예산 준수와 집계 개수 일치. 선택 변경 시 ELK·그래프 입력 재생성 없음 |
| 수집 | 요청 경로 전체의 최대 동시성 보장, 계정 수에 따른 체크포인트 복사량·최대 힙·IAM 호출 수 비교 |

각 코드 변경은 관련 단위 테스트와 `npm run build`를 실행한다. UI·인증·API 변경은 가짜 live 서버로 관련 `npm run test:e2e`도 실행한다. 전체 변경을 합칠 때 전체 테스트를 한 번 확인한다. 제공자 SDK는 가짜 응답으로 페이지 분할·빈 성공·부분 실패·권한 거부·취소를 검증한다.

선택 수집과 저장 분리는 특히 미선택 데이터의 값·완료 시각 보존, 성공한 빈 영역만 삭제, 다른 권한 범위 노출 방지, 프로세스 중단 후 마지막 정상 세대 복구를 통과해야 한다. 실제 계정 처리량·GCP 비용 적재·프록시 반복 수집은 실계정 작업 요청이 있을 때 별도로 검증한다.

## 추가 확인한 공식 자료

- IAM 대량 조회는 페이지 처리가 필요하고 사용자 상세에 MFA·접근 키 정보가 모두 포함되지는 않는다. `GetAccountAuthorizationDetails` 전환은 추가 권한과 누락 필드 보완을 검증한 후 판단한다. 먼저 기존 호출의 제한된 병렬화·중복 제거를 적용한다. [AWS API](https://docs.aws.amazon.com/IAM/latest/APIReference/API_GetAccountAuthorizationDetails.html), [UserDetail 필드](https://docs.aws.amazon.com/IAM/latest/APIReference/API_UserDetail.html).
- Secure 쿠키에는 localhost 예외가 있어 HTTP라는 이유만으로 장애를 확정할 수 없다. localhost·127.0.0.1·HTTPS 프록시를 브라우저로 재현한다. 공유 주소의 보안을 낮추지 않고 신뢰할 프록시 범위를 명시한다. [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie), [Express 프록시 설정](https://expressjs.com/en/guide/behind-proxies/).

## 구현 진행과 검증 기록

최초 계획 작성 뒤 구현 요청을 받아 개선을 반영했다. 현재 단위 테스트 189개, 빌드, 전체 E2E 63개(운영 세션 매트릭스 3개 포함)가 통과했다. 최종 통합 실행과 미검증 범위는 [구현 기록](issue-8-implementation.md)을 기준으로 확인한다. 실제 클라우드 수집·배포·이슈 본문·댓글 게시·이슈 종료는 수행하지 않았다.
