# Cloud Atlas 인수인계

이 문서는 Cloud Atlas를 참고해 **다른 서비스를 개선하는 개발자와 AI 에이전트**를 위한 지시서입니다. 이 레포는 코드를 옮겨 오는 원본이 아니라 설계를 보여주는 참고 구현입니다.

## 작업 방법

1. 이 문서를 먼저 읽습니다.
2. 대상 서비스의 스택, 데이터 모델, 화면을 파악하고 아래 설계와 비교합니다.
3. 적용할 항목과 제외할 항목, 영향을 받는 파일을 계획으로 제안하고 **확인을 받은 뒤** 구현합니다.
4. 코드를 복사하지 말고 대상 서비스의 구조와 코드 스타일로 다시 구현합니다. 이 레포의 긴 한 줄 코드 스타일은 따르지 않습니다.

## 무엇을 만든 것인가

AWS, Azure, GCP의 자원을 읽기 전용 API로 수집해 관리 계층과 네트워크 토폴로지로 탐색하는 포털의 프로토타입입니다. React, @xyflow/react, ELK, Express를 사용합니다. 타당성 검토와 근거 문서는 [feasibility-review.ko.md](feasibility-review.ko.md)에 있습니다.

```bash
npm install
npm run dev
npm test
npm run test:e2e
```

주소 뒤에 `?scenario=enterprise`처럼 붙이면 예시를 고를 수 있습니다. 값은 `single-vm`, `web-tier`, `gke-app`, `hybrid-vpn`, `standard`, `enterprise`입니다.

## 가져올 설계

### 1. 관리 범위에서 토폴로지로 내려가는 탐색

- 첫 화면에 3사의 조직 계층을 트리로 나란히 보여줍니다. Azure는 테넌트, 관리 그룹, 구독이고, AWS는 조직, OU, 계정이며, GCP는 조직, 폴더, 프로젝트입니다.
- 각 행에는 하위를 합산한 자원 수와 이상·중지 개수를 표시합니다.
- 행을 누르면 그 범위로 필터링한 토폴로지가 탭으로 열립니다. 그룹을 누르면 하위 범위 전체가 열립니다.
- 탭마다 펼침 상태를 기억합니다. 화면, 범위, 예시는 URL에 담아 뒤로가기와 링크 공유가 되게 합니다.

### 2. 토폴로지 배치

- 사내망에서 시작해 왼쪽에서 오른쪽으로 읽습니다. 전용선·VPN, 허브, 스포크 순서입니다.
- 선 방향은 사내망으로부터의 그래프 거리로 정합니다. 데이터의 source와 target 방향에 의존하지 않으므로 어떤 구성이 들어와도 같은 규칙으로 그려집니다.
- 좌표는 저장하지 않고 ELK layered로 계산합니다. **클라우드마다 따로 배치**해서 한쪽을 펼쳐도 다른 클라우드의 내부 배치는 바뀌지 않습니다. 사내망 연결은 각 배치에 넣은 보이지 않는 입구 노드로 경로를 받아 이어 붙입니다.
- 한 허브에만 연결된 형제 네트워크가 셋 이상이면(허브-스포크) ELK에 맡기지 않고 격자로 묶습니다. 허브에서 격자 가장자리까지는 ELK가 경로를 잡고, 격자 안에서는 공유 차선(왼쪽 차선 → 행 통로 → 열 차선)으로 각 스포크에 이어 붙입니다. 스포크가 한 줄로 길게 쌓여 지도가 세로로 가늘어지던 문제를 이것으로 해결했습니다. `tests/layout.test.ts`가 겹침, 경로 누락, 가로세로 비율을 검사합니다.
- 큰 그래프에서 화면이 멈추지 않도록 워커에서 실행하고, 입력이 같으면 캐시를 씁니다. 테스트는 `setLayoutEngine`으로 ELK를 같은 프로세스에서 돌립니다.
- 펼칠 때는 누른 컨테이너의 화면 위치를 고정합니다.
- 강조 표시는 배치와 분리합니다. 선택할 때마다 다시 배치하면 화면이 움직이기 때문입니다.

### 3. 규모 대응

- `개요 / 서브넷 / 전체` 단계와 컨테이너별 접기를 제공합니다. 자원 수에 따라 시작 단계를 고릅니다.
- 접힌 컨테이너로 향하는 관계는 보이는 조상으로 올려 쌍마다 선 하나로 묶습니다. 선을 누르면 묶인 관계와 근거를 모두 보여줍니다.
- 축소하면 세부 정보를 숨기고 이름을 키웁니다.
- 연결이 없는 같은 크기 자식은 세로로 쌓지 않고 격자로 묶습니다.
- 전체가 읽을 수 없을 만큼 작아지면 전부 맞추지 않고 입구부터 보여줍니다.
- CSP가 실제로 여러 리전에 걸칠 때만 리전 프레임을 만듭니다.

### 4. 분석

- **라우팅 규칙:** 피어링은 전이되지 않습니다. 탐색 상태에 "어떻게 도착했는가"를 담아, 게이트웨이 전이 플래그와 UDR이 있을 때만 다음 구간으로 넘어갑니다. 구현은 `shared/topology.ts`의 `buildRouting`입니다.
- **경로 추적:** 위 규칙을 적용한 최단 경로를 보여주고, 거치는 지점의 정책과 기본 경로를 함께 표시합니다.
- **단절 영향:** 자원을 뺀 뒤 사내망에 도달하지 못하게 되는 자원을 계산합니다. 이중화된 회선이 있으면 영향이 0건으로 나옵니다.
- **노출 후보:** 공인 IP와 넓은 인바운드 규칙이 함께 있는 자원을 모읍니다. 실제 노출로 단정하지 않습니다.
- **변경 이력:** 수집할 때마다 이전 스냅샷을 보관하고 차이를 계산합니다. 성공한 수집끼리만 비교해야 일시적 실패를 삭제로 오인하지 않습니다.

### 5. 수집 구조

- 로그인 상태를 감지하고 볼 수 있는 범위를 자동 탐색합니다. 클라우드끼리 독립적으로 수집하므로 하나가 실패해도 다른 클라우드와 마지막 스냅샷에 영향이 없습니다.
- 권한이 없는 서비스나 범위는 건너뛰고 `incomplete`로 기록합니다. 이 범위의 빈자리는 삭제로 보고하지 않습니다.
- 수집기의 HTTP·SDK 경계를 주입할 수 있게 만듭니다. 목데이터도 실제 응답 형태로 같은 페이지 처리와 정규화 코드를 거칩니다.
- CSP별 응답을 공통 `Resource`, `Link`, `HierarchyNode`로 정규화합니다.
- 계정 간 참조는 전체 수집을 합친 뒤에 해석합니다. 그래야 다른 계정의 VPC를 미수집으로 오판하지 않습니다.

### 6. 운영 화면

- **조치 목록:** 상태 이상, 노출 후보, 대역 중복, 특권 주체, 비용 급증을 `shared/findings.ts`가 하나의 우선순위 목록으로 모읍니다. 각 항목은 근거를 담고 해당 화면으로 연결됩니다. 여러 계정의 같은 문제는 한 줄로 묶습니다.
- **비용:** 진행 중인 달은 지난달과 그대로 비교하지 않고 월말 추정치와 비교합니다. 급증은 완료된 두 달만 비교합니다. 통화가 섞이면 합계를 내지 않습니다. 비용 API는 과금되므로 자원 수집과 주기를 분리했습니다.
- **IAM:** 역할 할당을 주체 기준으로 묶어 보여줍니다. 실효 권한으로 표시하지 않습니다.
- **연결 가이드:** 첫 접속에 CSP별 절차와 권한을 보여주고, 닫으면 목데이터로 볼 수 있습니다.

## 지켜야 할 규칙

- 구독, 계정, 프로젝트를 네트워크 경계로 그리지 않습니다. 소유 범위는 라벨로 표시합니다.
- NSG, 보안 그룹, IAM을 경유 장비처럼 선 가운데에 놓지 않습니다. 대상에 적용되는 관계로 표현합니다. Azure Firewall 같은 실제 경유 장비만 노드로 둡니다.
- 구성 관계, 정책, 관측된 통신을 구분합니다. 구성이 있다고 통신이 된다고 표현하지 않습니다.
- 범위 필터를 걸어도 사내망까지의 경로는 `범위 밖`으로 접어서 남깁니다.
- 권한이 없어 읽지 못한 참조를 지우지 않습니다. `조회 권한 없음`으로 남깁니다.
- 조직 API를 읽지 못해도 화면을 비우지 않습니다. 평면 목록으로 보여주고 이유를 안내합니다.
- 예제 값은 실제 값처럼 보이지 않게 표시합니다. 실제 수집 모드에는 시뮬레이션 데이터가 들어갈 수 없도록 검증합니다.
- 클라우드 인증 정보를 브라우저에서 받지 않습니다. 수집은 서버 측 읽기 전용 자격 증명으로 합니다.
- 실제 데이터 API는 접근 제어가 없으면 응답하지 않습니다. 범위 제한은 화면이 아니라 서버에서 적용합니다.

- `server/skus.ts`의 축약된 사양표. 실제 서비스는 SKU API를 조회해야 합니다.

- `server/auth.ts`의 토큰 방식. 범위 필터링만 참고하고 인증은 사내 SSO로 교체합니다.
- 코드 스타일과 인라인 CSS 구조

## 검증 상태와 한계

- **실제 계정 호출 전입니다.** 수집기는 진짜 클라우드에서 실행된 적이 없고, 목데이터의 응답 형태도 직접 작성한 것입니다. 필드 차이가 있을 수 있으니 대상 환경에서 먼저 대조하세요.
- **경로와 영향은 후보입니다.** 피어링 전이 규칙과 Azure UDR은 반영하지만, 경로 우선순위, BGP 상태, 방화벽 판정, 실제 패킷은 확인하지 않습니다. AWS와 GCP 라우팅 표는 수집해 표시만 하고 탐색 규칙에는 쓰지 않습니다.
- **변경 이벤트는 없습니다.** 주기 수집(기본 1시간)으로 전체를 다시 읽습니다. 이력은 파일에 30개까지 보관합니다.
- **비용 금액은 추정 차이가 있습니다.** 할인, 약정, 세금 처리가 CSP마다 달라 청구서와 다를 수 있고, 월말 예상은 일평균 단순 계산입니다.
- **IAM은 역할 할당까지입니다.** Azure Entra 역할, PIM, AWS SCP와 권한 경계, GCP 거부 정책은 평가하지 않습니다. 인터넷 공개 판단도 구성 기반 후보입니다.
- **SSO는 없습니다.** 해시로 비교하는 접근 토큰과 범위 제한까지만 구현했습니다.
- **성능은 자원 약 530개까지만 확인했습니다.** 이 규모에서 `전체` 단계는 한 화면에 읽을 수 없어 범위 탭으로 들어가는 사용을 전제합니다.
- **자동 테스트:** `tests/`는 수집, 정규화, 라우팅, 인증, 이력을 검증하고 `e2e/`는 프로덕션 빌드로 화면 동작을 검증합니다. 실제 CSP 응답과의 대조는 포함되지 않습니다.

## CSP 아이콘

`src/assets/csp-icons/`의 아이콘은 각 CSP의 공식 패키지에서 원본 그대로 복사했으며 권리는 각 제공사에 있습니다. 대상 서비스에 넣기 전에 [NOTICE.md](../src/assets/csp-icons/NOTICE.md)의 조건을 확인하세요. Azure는 아키텍처 다이어그램, 교육 자료, 문서 용도로 허용합니다. 제품으로 공개하거나 판매하려면 조건을 다시 확인해야 합니다.
